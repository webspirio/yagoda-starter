# Від'ємне «Пустих на точці» на `/crates` — ручне тестування, 2026-09-30

## Що перевіряли

Чи можна звичайними діями в системі зробити так, щоб на сторінці `/crates`
картка «Пустих на точці» (`on_hand` з `GET /crate-standing`) стала від'ємною.

Формула (`backend/src/crates/crate-standing.service.ts`):

```
on_hand = received − Σ видано + Σ повернуто − Σ ящиків-тари на ВСІХ живих квитанціях − Σ бій
```

`received` рахує тільки трансфери зі статусом `accepted` (кількість з трансферу),
`disputed` (`reported_crates`, а після розв'язання — `resolved_crates`), і лише
неанульовані. `sent` дає 0.

**Жодна дія не перевіряє залишок пустих перед записом** — ні видача, ні
квитанція, ні закриття зміни з боєм, ні анулювання трансферу чи повернення,
ні розв'язання спору. Сервіс прямо пише «MAY be < 0 when the documents disagree
(§6.9 — shown red)», тож мінус — задокументована поведінка, а не аварія. Питання
до власника: чи мають якісь із кейсів нижче блокуватися, а не лише
підсвічуватися червоним.

## Умови

- Локальний dev-стек (`docker compose up`), бекенд `localhost:3000`, фронт `localhost:5173`.
- Власник: `admin` / `admin`.
- Кожен кейс — окрема нова точка `NEG1`…`NEG7` (наділ `target_crates = 100`), свій
  оператор `opneg1`…`opneg7` / `password123`, свій постачальник `Sup NEGn`,
  зміна відкрита оператором з касою `0.00`.
- Ящикова тара — `чешка` (єдиний тип тари з `is_crate = true`).
- Кроки виконано через API тими ж ролями, що й в UI (відкрити зміну й
  прийняти/оскаржити трансфер — оператор; створити/анулювати/розв'язати
  трансфер — власник). Результат перевірено на `/crates` під оператором точки
  (Playwright + Chrome): число червоне, під карткою — «Пустих менше нуля:
  документи не сходяться — перевірте перекази, видачі, повернення, квитанції та бій».

## Кейси

| 2 | Трансфер відправлено, але не прийнято | Власник: трансфер 20 (статус `sent`) → видати 10 | **−10** | 10 | 0 | 0 | 100 |
| 3 | Анулювання прийнятого трансферу після видачі | Трансфер 20 → прийняти (пустих 20) → видати 15 (пустих 5) → власник анулює трансфер | **−15** | 15 | 0 | 0 | 100 |

### Нотатки по кейсах

1. **Видача без трансферу.** Найпростіший шлях: нова точка, `received = 0`, будь-яка
   видача одразу дає мінус. Ні бекенд, ні форма «Видати ящики» не знають про залишок.
2. **`sent`-трансфер.** Ящики «в дорозі» не рахуються, поки оператор не натисне
   «Прийняти». Якщо видати їх до прийняття — мінус, який зникне після прийняття.
   Практично ймовірний сценарій: машина приїхала, ящики роздали, трансфер не прийняли.
3. **Анульований трансфер.** Власник може анулювати вже прийнятий трансфер, з
   якого ящики вже роздано; нічого не перераховується, `received` просто падає.
   Відповідає коментарю «NOTHING IS SNAPSHOTTED: voiding an old receipt or transfer
   moves the figures silently».
4. **Спір.** Поки спір відкритий, рахується `reported_crates` оператора; власник
   розв'язує меншим `resolved_crates` без перевірки, що стільки вже видано.
5. **Бій.** `broken_crates` при закритті зміни обмежений лише `0…10000`. Тут
   від'ємним стає навіть «Усього за точкою» (`total = −15`), а «Не вистачає до
   наділу» (115) перевищує сам наділ (100) — найдивніший стан з усіх.
6. **Анульоване повернення.** Повернення можна анулювати, коли його ящики вже
   видано іншому. Постачальник A знову «винен» 10, B теж тримає 10 → у людей 20,
   хоча фізично їх 10.
7. **Квитанція.** «Повні ящики завжди наші» (клієнт, 2026-09-23): кожна одиниця
   ящикової тари на живій квитанції списується з пустих, навіть якщо пустих на
   точці не було. Поки зміна відкрита, `з ягодою = 12` врівноважує `Усього = 0`;
   після закриття зміни «з ягодою» обнулиться, а −12 залишиться.

## Спостереження

- Мінус ніде не блокується — лише підсвічується (UI відпрацьовує коректно:
  червоне число + попередження).
- Кейси 1, 2, 7 — «документ про надходження пустих ще/взагалі не внесено».
  Кейси 3, 4, 6 — «заднім числом зменшили надходження / збільшили видачу».
  Кейс 5 — введене вручну число без верхньої межі.
- Кейс 5 — єдиний, де від'ємне й `total`, і `shortfall > allotment`; якщо щось
  варто обмежувати першим, то, ймовірно, `broken_crates ≤ on_hand` при закритті.

## Повторний прогін у браузері (усе через UI)

Ті самі сім кейсів пройдено ще раз, **лише кліками в інтерфейсі**: Playwright
керує Chrome, мова інтерфейсу українська, API напряму не викликали. Для кожного
кейсу окрема точка `Браузер BR1`…`BR7` (код `BRn`, «Ціль ящиків» 100). Оператор
`br1`…`br7` / `password123`.

Сетап кожної точки:

1. `admin` / `admin` → **Точки прийомки → Нова точка** (назва, код, ціль ящиків 100).
2. **Користувачі → Новий користувач**: роль «Приймальник», точка `Браузер BRn`.
3. Вхід оператором через форму логіну → **Каса за день → Відкрити зміну** (у шухляді 0).
4. **Постачальники → Новий постачальник** («Без номера»).

### Що видно лише в UI

- **Жодна форма не попереджає заздалегідь.** «Видати ящики» не показує, скільки
  пустих є на точці, і видає будь-яку кількість до 10000. Мінус видно лише на
  картці `/crates` після запису.
- **Сторнування переказу** (кейс 3): діалог «Анулювати 0,00 ₴ · Браузер BR3?»
  говорить тільки про гроші. Він не згадує, що переказ віз 20 ящиків і що 15 з
  них уже видано.
- **Вирішення спору** (кейс 4): поле «Ящиків зараховуємо» приймає 5, хоча точка
  вже видала 20. Попередження немає.
- **Закриття зміни** (кейс 5): діалог сам підсумовує «Бій 25 · Відвантажено 25»
  на точці, де пустих лише 10, і записує це без жодного попередження.
- **Сторнування повернення** (кейс 6): UI правильно блокує сторнування видачі,
  на яку вже лягло повернення («спершу сторнуйте його»). Проте саме повернення
  сторнується, навіть коли його ящики вже видано іншій людині.
- **Прийомка** (кейс 7): форма перевіряє вагу («1,30 кг у ящику. Перевірте брутто
  або кількість тари»), але не кількість ящиків на точці.

## Прибирання

Точки `NEG1`…`NEG7` (API) і `BR1`…`BR7` (браузер) разом з їхніми операторами,
постачальниками, цінами й документами залишено в локальній БД для повторного
огляду. Для видалення: знайти `collection_points` з `code LIKE 'NEG%' OR code
LIKE 'BR%'` і видалити залежні рядки (зміни, документи, перекази, ціни,
користувачі, постачальники) разом з точкою.
