**Дата:** 2026-10-13 · **Статус:** погоджено в обговоренні (розділи 1–3), реалізація автономна
**Макети:** локальні, `reports/2026-10-13-issue-145/receipt-mockups.html` у головному checkout'і (не комітяться)

> **Правка 14.10.2026 (замовник, потім рев'ю PR #236).** Шапка друкує не імена, а номери:
> «Точка № N · Приймальник № M» (`collection_points.number`, `users.number` — `GENERATED
> ALWAYS`, видає база). Обидва номери приходять у відповіді на сам документ (`point_number`,
> `received_by_number` / `paid_by_number`), а не з довідника точок, тож квитанція не чекає на
> нього. Тип шапки — `{ point, staff }` (готові рядки), не `{ pointName, staffName }`. Опис шапки
> й відповіді сервера нижче — стан до правки.

## Що просить тікет

- **AK1.** Виплата без ягоди («Видати без ягоди», §3.7 — `payouts.intake_id IS NULL`) друкує
  квитанцію: видано готівкою, залишок, постачальник. Вигляд — як у звичайної квитанції, без
  блоку ягоди.
- **AK2.** Ім'я працівника — вгорі, біля назви точки, на всіх квитанціях. (Текст тікета каже
  «постачальника», але стрілка на зображенні веде від рядка «Приймав»; замовник підтвердив:
  **працівник**.)
- **AK3.** Стандартні шапка й футер; тіло — з секцій, щоб новий вид квитанції додавався
  розширенням, а не копіюванням розмітки.

## Рішення, погоджені з замовником

### Вигляд (однаковий для всіх квитанцій)

```
[АНУЛЬОВАНО / Причина: …]          ← лише для анульованого документа
          КВИТАНЦІЯ
     Кониців · Бондар Тарас        ← точка · прізвище ім'я працівника
- - - - - - - - - - - - - - - - -
№ квитанції      KON-PO-20261005-001
Операція                Видача боргу
Дата          5 жовтня 2026 · 09:40
Постачальник           Леонід Кастро
- - - - - - - - - - - - - - - - -
… секції тіла (ягода, ящики, підсумки) …
- - - - - - - - - - - - - - - - -
     <примітка мережі, якщо задана>
       Дякуємо за співпрацю!
       Не є фіскальним чеком
```

- Заголовок — завжди «КВИТАНЦІЯ». Тип документа — рядок «Операція» в реквізитах:
  «Прийомка ягоди» для квитанції прийомки, «Видача боргу» для виплати без ягоди.
- Рядок «Приймав» внизу зникає — працівник у шапці.
- Ім'я працівника — «Прізвище Ім'я» (`last_name first_name`).
- Футер — по центру, у такому порядку: примітка мережі (`network_settings.receipt_note`,
  задає власник; немає — немає рядків), фіксоване «Дякуємо за співпрацю!», дрібне
  «Не є фіскальним чеком». Наші квитанції не фіскальні (ПРРО) і не мають виглядати
  фіскальними.
- Текст «Квитанція збережена в системі. Дублікат можна роздрукувати будь-коли.» лишається
  тільки на екрані (він і раніше не друкувався).
- Квитанція видачі: реквізити → «Видано готівкою» (жирним) → «Залишок після видачі».
- Блок ягоди, повернення ящиків, «Нараховано / Видано готівкою / Залишок у цьому пункті» на
  квитанції прийомки — **без змін** у числах і рядках (поведінка «залишку зараз» на прийомці
  поза цим тікетом).

### Залишок на квитанції видачі — заморожений (варіант C)

Квитанція має бути детермінованою: її передрук будь-коли дає той самий папірець. Тому:

- нова колонка `payouts.balance_after numeric(12,2) NOT NULL` — борг постачальника на цій
  точці **одразу після** цієї виплати;
- пише її `PayoutWriter.write` як `sub(debt, amount)` (`common/money.ts`). `debt` він уже рахує
  під блокуванням постачальника (`withinSupplierLedger`) для стелі §3.5, тож значення точне і
  гонка двох виплат виключена. Покриває всі шляхи через `PayoutWriter` (видача без ягоди,
  виплата з прийомки);
- колонка — **запис надрукованого, а не джерело боргу.** Борг рахує лише `debtSql`; ніхто не
  читає `balance_after` для розрахунків. §3.2 («залишок — похідна, не поле вводу») не
  порушується. Це пишеться в Note таблиці в `28-db-schema.dbml`;
- анулювання виплати колонку не змінює: на квитанції — штамп, число — як було надруковано;
- на квитанції — дата й час виплати (`business_date` зміни + `created_at`, як у квитанції
  прийомки). Час друку не друкується — інакше кожен передрук відрізнявся б;
- імена (точка, працівник, постачальник) читаються з довідників наживо; перейменування
  змінює передрук. Прийнято: це довідкові дані, не гроші.

**Міграція наявних рядків.** Залишок відтворюється на момент кожної виплати `p`:

```
Σ intakes      i: i.supplier_id = p.supplier_id, i.created_at <= p.created_at,
                  (i.voided_at IS NULL OR i.voided_at > p.created_at)
+ Σ top-ups    t: те саме для t, і батьківська квитанція не анульована на той момент
− Σ payouts    q: q.supplier_id = p.supplier_id, q.created_at <= p.created_at,
                  (q.voided_at IS NULL OR q.voided_at > p.created_at)   -- включно з p
```

`created_at` у Postgres — час початку транзакції, тож якщо дві транзакції по одному
постачальнику чекали одна одну на блокуванні, порядок за часом може розійтися з реальним.
Це стосується лише історичних рядків; нові записуються точно. Міграція: додати nullable →
заповнити → `SET NOT NULL`.

### Відповідь сервера для виплати

`PayoutResponse` (і `GET /payouts`, і `GET /payouts/:id`, і відповідь на створення) отримує:

- `balance_after: string`;
- `paid_by_first_name`, `paid_by_last_name` (працівник, що видав);
Імена постачальника і точки сервер не додає: фронт бере їх через `useSupplierQuery` і
`usePointOptionsQuery`, як квитанція прийомки.

`IntakeResponse` отримує `received_by_first_name` / `received_by_last_name` поруч із
`received_by_name`, щоб шапка друкувала «Прізвище Ім'я».

## Будова на фронті (AK3)

- **`shared/ui/receipt`** — модель і рендер, без доменних імпортів:
  ```ts
  type ReceiptRow = { label: string; value: string; strong?: boolean; muted?: boolean };
  type ReceiptSection =
    | { kind: 'rows'; rows: ReceiptRow[]; subtext?: string[] }  // реквізити, підсумки
    | { kind: 'berryLine'; … }                                  // брутто/піддон/тара/нетто/ціна/сума
    | { kind: 'note'; text: string };                           // «повернення ящиків анульовано» тощо
  type ReceiptDocument = {
    voided: { reason: string } | null;
    header: { pointName: string; staffName: string };
    sections: ReceiptSection[];
    footer: { note: string | null };
  };
  ```
  `ReceiptView` малює штамп, шапку («КВИТАНЦІЯ»), секції через вичерпний `switch` по `kind`,
  футер. Тільки його корінь має клас `.printable`, тож правила друку в `index.css` не
  змінюються.
- **Збирачі** — чисті функції в `widgets/receipt/model`: `buildIntakeReceipt` і
  `buildPayoutReceipt`. Переклад і форматування роблять вони; у моделі — готові рядки. Сума
  не рахується на фронті, лише форматується.
- `ReceiptSheet` замінюється на `ReceiptView`; `ReceiptDialog` (прийомка) складає документ
  збирачем. Новий `PayoutReceiptDialog` — те саме для виплати.

## Де друкується квитанція видачі

1. Одразу після успішної «Видати без ягоди» (сторінка «Борги», картка постачальника)
   відкривається квитанція видачі з кнопкою «Друк». Тост лишається.
2. Рядок виплати **без ягоди** у «Дні», «Журналі» (вкладка виплат) і в історії картки
   постачальника відкриває ту саму квитанцію.
3. У вікні квитанції — «Анулювати» за наявними правилами (§9.4, `canVoid` виплати) через
   наявний `VoidDocumentDialog`.
4. Виплати з прийомкою (`intake_id` не NULL) окремої квитанції не мають — вони на квитанції
   прийомки, як і раніше.
