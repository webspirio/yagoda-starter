# Intake Top-Up UI (#61) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the owner a way to add «фантомний залишок» against a recorded receipt, and give both roles a timeline that explains why a supplier is owed what they are owed.

**Architecture:** A new `entities/intake-top-up` read slice and a `features/top-up-intake` write slice, composed into the existing supplier card. `features/void-document` gains a fourth kind rather than growing a parallel void dialog.

**Tech Stack:** React 19, TanStack Query v5, react-hook-form, Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-09-15-yagoda-mock-ui-catchup.md` (section 4)

## Global Constraints

- Money is a DECIMAL STRING end to end. Totals go through `shared/lib/money`'s `sum`/`cmp`; never `Number()`.
- Both create and void are `@Auth(UserRole.NetworkOwner)`. The buttons are therefore **ABSENT** for an operator, never disabled — §10.2: «заблокована кнопка вчить шукати обхід, відсутня не вчить нічого».
- `reason` is REQUIRED and must be NON-BLANK on both create and void (`@Length(1,500)` plus `\S`). It is the entire point of #61: «щоб при перегляді історії було ясно зрозуміло, чому ми маємо викладати дві тисячі цьому постачальнику».
- A top-up has NO code, NO business date and NO shift. It borrows all three from its parent intake, two hops to the supplier. Do not invent a code for the timeline.
- `counts_toward_balance` is FALSE when either the top-up **or its parent intake** is voided. A row whose parent was voided is still LIVE and must still be listed — hiding it is the silence the flag exists to prevent.

### Task 3: The supplier card

**Files:**
- Modify: `frontend/src/pages/supplier-card/ui/SupplierCardPage.tsx`, `SupplierTimeline.tsx`, `SupplierCardPage.test.tsx`
- Modify: both locale files

- [ ] **Step 1: Add the third row kind to the timeline**

`TimelineRow` gains `| (TimelineRowBase & { kind: 'topUp'; topUp: IntakeTopUp })`. A top-up has no `code` and no `business_date`, so those columns render the PARENT's code and nothing for the date — the merge sorts on `created_at`, which every kind has.

A row with `counts_toward_balance === false` renders struck through with a caption saying WHICH of the two was voided:
- the top-up itself voided → its own `void_reason`
- the PARENT voided → `supplierCard.timeline.parentVoided`

That distinction is the point: the two look identical on a balance and are completely different events.

- [ ] **Step 2: «Додати залишок» on an intake row**

Owner only. It opens `TopUpDialog` for that receipt. An intake row that is ITSELF voided offers nothing — a top-up on a voided receipt counts for nothing the moment it is written.

- [ ] **Step 3: Count top-ups in the tiles**

The «Нараховано» tile currently sums live intakes. The balance is `Σ intakes + Σ top-ups − Σ payouts`, so a tile that ignores the middle term will visibly disagree with the balance tile beside it. Add the live top-ups (`counts_toward_balance === true`) to `accrued`, and extend the truncation hint to the third journal.
